Prompt engineering is writing the request itself well: instructions, examples, an assigned role, a
required format, and sometimes an explicit ask to reason before answering. It does not change what
level a technique sits at — this is still level 1, one call, decided entirely by code — it changes
what happens inside that one call, by giving the model more to work with than the bare question
alone.

Every maker that publishes a model also publishes its own guidance for this, because the moves
(structure, examples, a stated format) carry across models even though the details of how much
each one helps do not<Cite n={1}/><Cite n={2}/><Cite n={3}/>. None of it is worth doing once and
trusting forever: write down what a correct answer looks like before changing a prompt, then check
the new version against the same cases the old one had to pass. This page's example makes that
concrete — the same question and the same source text, asked two ways, checked by a regular
expression rather than by reading the reply and deciding it looks better.

<Lane name="use" title="Use it">

Most people already do some of this; it is usually one clause added on the fly ("be concise",
"answer as a table") rather than a deliberate practice. The makers' own guides describe it as a
handful of moves that hold up across their different models.

**Instructions.** Say exactly what you want, not what you do not want. "Answer in two sentences"
gets followed more reliably than "don't be too long."

**Examples.** Show, not just tell, especially for a format that is hard to describe in words.
OpenAI's guide calls one well-chosen example "few-shot learning"<Cite n={1}/>, and Google's
guide goes further, recommending that few-shot examples always be included rather than left
out<Cite n={3}/>.

**A role.** Telling the model who it is for this conversation ("you are a parts-desk assistant")
narrows what a plausible answer looks like, the way a job title narrows what a person would say
next.

**A format.** Asking for the answer as a specific shape makes the reply something code can check
automatically instead of something a person has to read and judge. Google's own guide gives this
example directly: ask for a response "as a table, bulleted list, elevator pitch, keywords,
sentence, or paragraph"<Cite n={3}/> and that is what comes back.

**Asking for reasoning.** For a question with more than one step, asking the model to work
through it before giving a final answer tends to help, at the cost of more tokens and more time;
OpenAI's guide notes this matters less for a model built to reason on its own by default, which
tends to do better on high-level guidance than on very precise, spelled-out steps<Cite n={1}/>.

**Iterating against test cases.** Anthropic's guide frames this as the starting point, not an
afterthought: it assumes you arrive with a clear definition of success and a way to test against
it, and says to establish both first if you do not have them<Cite n={2}/>. Then check a new
version against the same cases the old one had to pass. A prompt that "feels" better after one
try is a different claim from a prompt that scores better across cases it was not tuned on.

In a chat app, all of this still applies with no API in sight: a saved custom instruction, a
pinned example message, or just typing "answer in a table" each session are the same moves,
done by hand instead of programmed once.

</Lane>

The example runs the exact contrast above: the same question, against the same source passage,
sent to the model two ways. The structured prompt adds a role, an explicit two-field output
format, and one worked example — the moves OpenAI's and Anthropic's guides both
describe<Cite n={1}/><Cite n={2}/>. The bare prompt is the question and the passage with nothing
else added.

The check at the end is what turns "did structure help" into something answerable rather than a
matter of taste: `FIELD_RE` looks for exactly `PART: <something> PRICE: <something>` in the reply.
Against this site's `StubModel`, the two replies are scripted by hand for the test that exercises
this example — a well-formatted two-line answer for the structured run, and a hedging sentence
that never states a part number in that shape for the bare one. That is an honest limit on what a
stub run can show: it demonstrates the check a real prompt-tuning loop is built from, not a
finding about how any real model responds to more or less structure. The citations above are the
actual claims about real models; this example is the machinery for testing your own.

<WhenNot>

Skip adding structure if the bare question already gets the right answer every time you try it —
structure has its own cost: more tokens on every call, and a format instruction that itself needs
testing. And if the format absolutely must be valid on every single call rather than usually
valid, use <Link href="/techniques/structured-output/">structured output</Link> instead of an
instruction alone: a schema is enforced by the API, a format instruction is only a strong
suggestion the model can still miss.

</WhenNot>

## How to eval it

<HowToEval questionCount={60} kinds={['lookup', 'multi-hop', 'numeric', 'unanswerable', 'conflicting sources']}>

Prompt engineering is not its own row in the site's eval; it is a way of improving the score at
whichever level you are already using, by holding the retrieval, the tools and the level fixed and
comparing prompt versions against the same 60-question set (`docs/EVALS.md`). The right test is
A/B, not before/after: run the old prompt and the new prompt over the same questions and compare
scores, since a single "it reads better now" impression on a handful of examples is exactly the
failure the iterating-against-test-cases move above exists to catch.

`scripts/eval_run.py` will not score this example against that set: it sends one fixed passage
to the model two ways and never reads the documents the questions are about, so asking the
runner for a score prints that reason and stops (`docs/EVALS.md`). What to measure for a prompt
change is the pair, old prompt against new, on the same inputs: format adherence, the share of
replies that come back in the shape you asked for, and accuracy of what is in them.

</HowToEval>
