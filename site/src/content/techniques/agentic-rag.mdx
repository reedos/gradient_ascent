Agentic RAG puts the search loop itself under the model's control. <Link
href="/techniques/rag/">RAG</Link> always searches once and asks the model once. Agentic RAG
instead offers the model a search tool it can call as many times as it decides it needs, lets it
read what comes back, and lets it decide whether to search again, read more closely, or stop and
answer: the <Link href="/techniques/single-agent/">single-agent</Link> loop aimed at retrieval.

Google describes its own version this way: "at each step, the model has to ground itself on all
information gathered so far, then identify missing information and discrepancies it wants to
explore," continuing until "the model determines enough information has been gathered"<Cite
n={1}/>. OpenAI's deep research models work the same way: "agentic" systems that "conduct
multi-step research" and return a listing of every search made along the way<Cite n={3}/>. In both
cases the model chooses the next query and when to stop; your code still runs every search and can
cut the loop off with a hard cap regardless of what the model would have done next.

This page is marked draft, not published: agentic RAG has no recorded trace and no scored result
file yet, so nothing below is measured. It is illustrated. The home page's own comparison runs one
question through both RAG and this technique side by side.

<Lane name="use" title="Use it">

This is what a deep-research mode in a chat app is doing. ChatGPT, Claude, Gemini and Perplexity
each ship one; SpaceXAI's Grok has DeepSearch. Ask a question, and instead of one search the
product runs several, reads what each one turns up, and decides for itself whether it has enough
or needs to look further before writing a report.

Google's description of its own Deep Research is specific about the mechanism: the model
"oversees the execution of" a research plan and "at each step the model reasons over information
available to decide its next move," browsing "the web and your Gmail, Drive, and Chat if you
choose so"<Cite n={1}/>. This is the same search-then-read-then-decide loop the run above steps through,
aimed at a much larger set of sources. OpenAI's documentation for its deep research models
describes the output the same way: it "will contain a listing of web search calls, code
interpreter calls, and remote MCP calls made to get to the answer," so the searches themselves are
visible, not just the final report<Cite n={3}/>.

That visibility is worth using. A deep-research report that shows its sources or its search steps
is showing you the trace this page's run diagram illustrates in miniature: check whether a claim
in the report actually traces back to one of the searches shown, the same way you would check
RAG's citations, and watch for a report that cites a source it never appears to have opened.

The loop also has a cap you do not see. OpenAI documents a `max_tool_calls` parameter a developer
can set when creating a deep research request, "to control the total number of tool calls (like to
web search or an MCP server) that the model will make before returning a result"<Cite n={3}/>; the
products built on this pattern have some version of the same limit. A
report that reads as thinner than the question deserved, especially on something with several
parts to it, may be a run that hit its cap rather than one that ran out of things to find.

Ask questions this is actually for: ones where the right next search depends on what the last one
found, or where the answer draws on several documents that disagree. A question one search can
already answer does not need this, and costs more here for no benefit. See when RAG alone is
enough, below.

</Lane>
<Lane name="build" title="Build it">

`examples/agentic_rag/` is the site's running example for this page; nothing new was written for
it here. It offers the model two tools, `search(query)`, which returns titles and citations but no
text, and `read(cite)`, which returns one section's full text, and loops until the model stops
calling tools or a cap is hit. Withholding the text from `search` is what makes the loop genuinely
iterative rather than a slower RAG: the model has to decide, itself, which of the titles it saw are
worth opening before it can cite anything with confidence.

Every tool call and the decision to stop are `decided_by: "model"`: the model's own output picks
the query, picks which section to read, and picks when it has enough. Running a tool and returning
its result to the model are always `decided_by: "code"`, the same rule
<Link href="/techniques/single-agent/">single agent</Link>'s example follows. `MAX_STEPS` (6) and
`MAX_TOKENS` (4000) are the hard caps; when either is hit before the model stops on its own, the
code forces one last no-tools call for a final answer, and that forced stop is `decided_by:
"code"`: the model never chose to stop, so it is not credited with a decision it did not make.

Anthropic's account of building a production research agent puts a number on what a loop like this
costs, and the published sentence carries two figures, not one: "In our data, agents typically use
about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens
than chats"<Cite n={2}/>. The 4× is the half that belongs on this page: one agent running its own
searches. The 15× is for the system of several agents Anthropic was describing, which is level 6,
not this one. Both are Anthropic's numbers, not anything measured here. Anthropic also lists what
went wrong in early versions of that system: agents "continuing when they already had sufficient
results, using overly verbose search queries, or selecting incorrect tools"<Cite n={2}/>, the same
failures a step cap and a careful stop condition exist to catch here, at a much smaller scale.

<WhenNot>

Try <Link href="/techniques/rag/">RAG</Link> first if one search, over one fixed set of documents,
can actually answer the question: most lookups can, and RAG costs one model call every time
instead of a number that varies with how hard the question turns out to be.

Try a fixed multi-step <Link href="/techniques/workflow-graphs/">workflow</Link> instead of an
agent if you already know how many searches a question needs and in what order: a two-step
chain that always searches, then always searches again with a refined query, is cheaper and more
predictable than a loop when the shape of the task never actually varies.

Move up to agentic RAG once the next query genuinely depends on what the last one found, so the
number of searches cannot be fixed in advance.

</WhenNot>

## How to eval it

<HowToEval questionCount={60} kinds={['lookup', 'multi-hop', 'numeric', 'unanswerable', 'conflicting sources']}>

`agentic_rag` is registered and scored on the same 60-question set as every other technique here:
exact or rubric match, citation hit rate, and the count of model-decided steps the trace carries.
Multi-hop and conflicting-source questions are where the extra cost is supposed to earn its
keep: a multi-hop question needs two sections found and used together, which single-pass RAG
often cannot do in one search, and a conflicting-source question needs the loop to notice two
retrieved sections disagree rather than stopping after the first one that looks like an answer. A
lookup question that RAG already answers in one call is the wrong place to look for agentic RAG's
advantage; if the extra cost does not show up as a better score on multi-hop and conflicting
questions specifically, it is not paying for itself.

No result file exists for agentic RAG yet, so this page cannot say a number for any of it. Run
`python scripts/eval_run.py --example agentic_rag --model <spec> --dry` to project the cost of a
real run before spending anything on one.
