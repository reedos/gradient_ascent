The Model Context Protocol, or MCP, is a standard way for an AI application to connect to servers
that expose tools, resources and prompts, instead of a developer wiring each integration by hand.
The protocol's own architecture overview names three participants: an MCP host is "the AI
application that coordinates and manages one or multiple MCP clients"; an MCP client "maintains a
connection to an MCP server and obtains context from an MCP server for the MCP host to use"; an
MCP server is "a program that provides context to MCP clients"<Cite n={1}/>. A host creates one
client per server<Cite n={1}/>.

MCP sits at level 4 for the same reason function calling does: a tool a server exposes is still
one fixed action your code carries out once the model picks it, inside a run your code bounds.
The line to level 5 falls in the same place too: one choice here, against a loop the model
leaves on its own in a <Link href="/techniques/single-agent/">single agent</Link>. What MCP
changes is not how much the model decides but where the tool definitions and the code that runs
them live: behind a protocol boundary any compliant host can speak, instead of wired into one
application's own tool-calling code.

This page is marked draft, not published: MCP has no recorded trace and no scored result file
yet, so nothing below is measured. It is illustrated.

<Lane name="use" title="Use it">

If a chat app or an editor lets you add a "connector" or "MCP server" from a directory, then ask
the model to use it, you have used MCP. Claude connectors work this way, and workflow builders
such as Langflow and Gumloop let a flow call tools from a connected MCP server the same way a
function-calling flow calls one defined inline. The point of the protocol is that the same server
works with any of these hosts, because they all speak the same requests underneath: list what a
server offers, read from it, or call one of its tools.

The protocol's documentation describes three things a server can offer, and is specific about who
is meant to decide each one: "Tools" are "functions that your LLM can actively call," and the
model decides when to use them; "Resources" are "passive data sources that provide read-only
access to information for context," and the application decides what to fetch; "Prompts" are
"pre-built instruction templates," and the user decides when to invoke one<Cite n={2}/>. A server that only
exposes resources cannot act on its own; one that exposes tools can, which is exactly the
distinction worth checking before connecting one.

Because a tool's description is what steers the model toward using it, and that description comes
from whoever wrote the server, the specification is direct about the risk: "clients MUST consider
tool annotations to be untrusted unless they come from trusted servers"<Cite n={3}/>. It also asks
for a person in the loop: "there SHOULD always be a human in the loop with the ability to deny
tool invocations"<Cite n={3}/>. One of the client behaviors it lists for that: "Show tool inputs
to the user before calling the server, to avoid malicious or accidental data
exfiltration"<Cite n={3}/>. A product that lets an MCP tool run with no visible confirmation for
anything beyond a lookup is not following that guidance.

</Lane>

<WhenNot>

Try <Link href="/techniques/function-calling/">function calling</Link> first if the tools your
code needs are the ones your own application defines: a protocol adds a client, a server
boundary and a message format to maintain, for no benefit if nothing outside your own codebase
will ever call those tools a different way.

Move up to MCP once more than one application needs the same tools, or the tools should come from
someone else's server (a database, a ticketing system, a search index) that you would rather
connect to than reimplement.

</WhenNot>

## Stateless MCP

"Stateless" is not shorthand here. The specification's own changelog uses the word directly: one
of its listed major changes for the current revision reads "Make MCP stateless: remove the
initialize/notifications/initialized handshake. Every request now carries its protocol version
and client capabilities in _meta"<Cite n={6}/>. This is the specification's own description,
not a blog post's paraphrase of something the spec calls by another name.

Two changes shipped together in the 2026-07-28 revision. That is the current one: the
specification's changelog describes it as what changed since the previous revision,
2025-11-25<Cite n={6}/>, and the maintainers' roadmap, updated August 22, 2026, refers to it as a
release already made rather than a proposal<Cite n={9}/>. The handshake is gone: earlier revisions opened a
connection with an `initialize` call and kept capabilities for as long as that connection lasted;
every request now states its own protocol version and capabilities instead. Protocol-level
sessions are gone with it, under a second entry in the same changelog: the revision removes
"protocol-level sessions and the Mcp-Session-Id header from the Streamable HTTP transport", and
"servers that need cross-call state use explicit, server-minted handles passed as ordinary tool
arguments"<Cite n={6}/>. The
transport specification says what that took away in practice: servers used to assign a session
via a header, clients could open a standalone stream to receive messages of their own, and a
broken stream could resume from where it left off: of all of it, the current revision states
plainly, "None of these mechanisms are part of this revision"<Cite n={5}/>. A current server that
receives an `Mcp-Session-Id` header from an older client is told to "ignore it, and do not mint or
echo session IDs"<Cite n={5}/>.

Why this was worth breaking backward compatibility over is stated in the proposal that became it,
SEP-2575, rather than in the changelog: the old handshake created "significant challenges
for scalability (load balancing requires sticky sessions), resilience (server failure loses
session state), and implementation complexity (both client and server must manage session
lifecycles)"<Cite n={7}/>. A load balancer that has to keep sending one client to the same backend
for the life of a session cannot freely spread requests across instances, and a serverless
platform that may run a different instance for every single request has nowhere to keep a session
at all; a protocol that asks nothing to be remembered between requests has nothing to lose when
the backend that handled the last one is gone. The companion proposal, SEP-2567, describes what
replaces a session for a server that genuinely needs state across calls: "Stateful workflows use
`create_*() -> handle` + threaded parameters (guidance, not a protocol construct)"<Cite n={8}/>:
an ordinary tool call hands back an identifier, and later calls pass it back as one of their own
arguments, the same as any other piece of data the tool takes, rather than something the
transport carries for you.

Both proposals are merged (SEP-2575 on May 11, 2026, SEP-2567 on May 7, 2026) and both changes are
in the 2026-07-28 revision: released, not proposed. What is still open is narrower. The
specification's own roadmap, updated
August 22, 2026, lists "capability scoping for tool lists after SEP-2575" among what its maintainers
want to look at next<Cite n={9}/>: a further refinement of what a stateless request can still
express, not a reconsideration of removing sessions in the first place.

boundary adds over calling a Python function directly. In this example that boundary is an
in-process function call, so the difference is the `tools/list` round trip and nothing else; over
a real transport it also carries network time this measurement will not show.
