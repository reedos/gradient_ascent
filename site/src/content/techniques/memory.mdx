Memory is keeping information from one conversation to the next. A chat has no memory of its
own beyond the messages inside it, so a product that seems to remember you is writing facts down
somewhere and reading them back into a later, otherwise unrelated conversation.

Two different things get called memory. A summary is a compressed account of what happened, cheap
to reread, but whatever it leaves out is gone. A record is closer to the raw fact (a purchase on
a date, a preference stated once) kept on its own and searched later. Letta draws that line in
its own product: a small "core" memory that stays in the context window, and a larger "archival"
memory that cannot be pinned there and has to be queried on demand with a search
tool<Cite n={3}/>. Mem0, which sells memory infrastructure for other people's products rather than
a chat app, states the record approach outright: memories accumulate, nothing is overwritten, and
a search returns the relevant ones<Cite n={2}/>.

Memory sits at level 2, context: every write, search and deletion here is your code's, and the
model only answers with what it was handed. This page is marked draft, not published: it has no
recorded trace and no scored result file, so nothing below is measured.

<Lanes>
<Lane name="use" title="Use it">

If a chat app has ever surprised you by remembering something from an earlier, separate
conversation (a preference, a project, a person you mentioned) you have used this. Several
chat apps have the feature now; the ones this site has checked are listed under Out there at the
foot of this page. They do not all behave the same way, so the three questions below are worth
asking of whichever one you use, rather than assuming what you learned from another.

**What is stored, and can you see it?** Anthropic documents Claude's answer: everything Claude
memory holds is listed by topic in the settings, and you can open any topic to read it, edit it,
or delete that one on its own. By default it does not store personal or sensitive subject matter
(health, race, ethnicity, religious beliefs, politics, gender identity and similar areas) unless
you turn that on<Cite n={1}/>.

**Who can see it?** In Claude, memory is per person: Anthropic says an account's owners
cannot view or edit an individual user's memories, and each project keeps its own separate memory
space<Cite n={1}/>. That is one maker's design, not an industry rule, which is why it is worth
checking on a shared or work account before you say something in front of one.

**How do you get rid of it?** Two controls that sound similar are not. Anthropic documents pausing
as keeping the existing memories while stopping new ones, and resetting as permanently deleting
all of them, project memories included, with no undo. And deleting the conversation does not
delete what it taught: Anthropic states that when a conversation expires or is deleted, the memory
entries generated from it are not removed, so you delete those separately<Cite n={1}/>. Assume
that is the default behavior elsewhere too until a product's own page says otherwise.

None of this is a reason to avoid the feature. It is a reason to open the settings page once,
since a memory that quietly gets everything right looks, from outside, exactly like one that got
something wrong a year ago and nobody has read since.

</Lane>
<Lane name="build" title="Build it">

The example below is a small store with the three operations that matter: `write`, `recall`, and
`forget`. It is handed a list of facts already stated: the extraction step a real product runs
to decide what is worth keeping is its own model call this example does not duplicate, since
<Link href="/techniques/knowledge-graphs/">the knowledge graphs example</Link> already shows that
shape (one model call, always made, that fills in content rather than choosing what happens
next). What this example shows instead is what happens after writing: `recall` ranks stored facts
by cosine similarity to a new question, the same mechanism as
<Link href="/techniques/embeddings-search/">embeddings and search</Link> and the same bag-of-words
stub embedder, just over a handful of personal facts instead of a document corpus. The scores
it prints show the mechanism and say nothing about how a real embedding model would rank them.
`forget` removes an entry outright; nothing recalled afterward can include it again, which is the
whole reason the operation exists rather than being another kind of write.

<WhenNot>

Try <Link href="/techniques/context-engineering/">context engineering</Link> first if everything
relevant is already in the current conversation. Memory only matters for information that has to
survive after a conversation ends: a single session never needs it.

Move to memory once a product needs to answer questions using something a user said in a
different, earlier conversation, not just the one open right now.

</WhenNot>

## How to eval it

<HowToEval questionCount={60} kinds={['lookup', 'multi-hop', 'numeric', 'unanswerable', 'conflicting sources']}>

The site's shared 60-question set is asked within a single sitting over one document set, so it
does not test what memory is actually for: a fact stated in one session and needed again in a
separate, later one. A fair eval for this technique would need its own question set, written as
pairs across sessions: a fact stated in session one, a question in session two that depends on
recalling it, and a check that a fact explicitly forgotten between sessions no longer affects the
answer.

So `scripts/eval_run.py` will not score this example: asking it to prints that reason and stops,
rather than returning a number measured on the wrong thing (see `docs/EVALS.md`). The three
measurements that would mean something here are recall of a fact written in an earlier session,
the share of answers that use a recalled fact when one applies, and a check that a forgotten
fact never reaches an answer again.

</HowToEval>
