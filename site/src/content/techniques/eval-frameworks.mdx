Evaluation frameworks is a page under <Link href="/techniques/evals/">evals</Link>: the tools that
run a golden set, grade what came back, and compare runs, instead of a team building that machinery
from scratch. What they do for you, in the shape <Link href="/techniques/evals/">the evals
page</Link> already describes generically, is: hold a dataset of examples, run a program or prompt
against every one of them, grade each result, and let two runs be compared. Some also record a
trace of what happened inside each run, not only the final answer.

Five of them are set out side by side below, described only in their own documentation's words, read
2026-09-18. There is no ranking and no "best for" here: what fits a team depends on things this
page cannot know — what is already being traced, who has to read a result, and whether the data
being graded may leave the machine at all. A sixth tool, OpenAI Evals, is mid-shutdown and is
reported separately rather than compared. <Link href="/techniques/prompt-optimization/">Prompt
optimization</Link> is the technique that consumes whatever one of these produces.

This page is marked draft, not published: no result from any of these tools exists for this site,
so nothing below reports a measured number.

<Lanes>
<Lane name="use" title="Use it">

Most people meet these tools as someone else's dashboard: "our evals run in Braintrust," "CI runs
promptfoo," "check the LangSmith experiment." Before trusting a number one of them reports, four
checks apply, each a version of a question <Link href="/techniques/evals/">the evals page</Link>
already raises about any score, now aimed at a tool a team adopted rather than built.

First, what graded it — a pattern match, or a model reading a rubric — and if a model graded it,
has anyone checked a sample of its verdicts against a person's own judgment? A dashboard that shows
one aggregate number rarely shows this by default; it is usually a setting or a second report
someone has to go looking for. Second, is the number comparable to the last one — same dataset, same
grading configuration, or did either one quietly change between runs? A framework that versions
datasets and grading configs separately makes this easy to check; one that does not makes it easy to
compare two different things without noticing. Third, were any items ungraded — a malformed grader
reply, a run that errored out — and were they excluded from the score or folded into it as a
failure? And fourth, if the tool is a hosted service, where does the data being graded actually go:
a locally run, open-source tool and a cloud dashboard answer that question very differently, which
matters most for anything that should not leave the machine it runs on.

None of these four checks require reading a line of the tool's code. They are questions to ask
whoever set the dashboard up, or checks to run once against a report before trusting the next ten.

</Lane>
<Lane name="build" title="Build it">

The same four questions, asked of five tools, answered out of each one's own current
documentation. Nothing below is this site's assessment of any of them.

**promptfoo.** Calls itself "an open-source CLI and library for evaluating and red-teaming LLM
apps." On where the data goes: "This software runs completely locally. The evals run on your
machine and talk directly with the LLM." No licence on the page read. Grading is metrics a user
defines over prepared test cases, displayed in "matrix views that let you quickly evaluate outputs
across many prompts"<Cite n={1}/>. Separately, promptfoo announced on 2026-03-09 that it was
joining OpenAI, saying "Promptfoo will remain open source and we will continue to serve users and
customers"<Cite n={10}/>.

**Braintrust.** Calls itself "the active observability platform for instrumenting, understanding,
and improving agents," with a workflow it names as instrument, observe, annotate, evaluate, deploy
and admin<Cite n={2}/>. On where the data goes: hosted, with a self-hosting guide that "offers a
self-hosted deployment option that separates data storage from platform management" — the customer
runs the storage, Braintrust runs the managed interface — and marks self-hosting as available only
on the Enterprise plan<Cite n={4}/>. No licence on the pages read. Grading is its autoevals
library, which "bundles together a variety of automatic evaluation methods including" LLM-as-a-judge,
heuristic (it gives Levenshtein distance) and statistical (BLEU)<Cite n={3}/>.

**LangSmith.** Describes itself through what it covers: observability, evaluation, prompt
engineering and deployment. On where the data goes: "cloud, hybrid, or self-hosted," and its docs
say all three options include those same four capabilities<Cite n={5}/>. No licence on the pages
read. Grading is "evaluators," which are "workspace-level resources that score application
performance," run over a dataset — "a collection of examples," where "an example is a test input,
reference output pair" — and each experiment "captures outputs, evaluator scores, and execution
traces for every example in the dataset"<Cite n={6}/>.

**DeepEval.** Calls itself "a simple-to-use, open-source LLM evaluation framework, for evaluating
large-language model systems." On where the data goes: its metrics "run locally on your machine,"
with an opt-in cloud — using the `deepeval` platform "will allow you to generate sharable testing
reports on the cloud." Licence: "DeepEval is licensed under Apache 2.0." Grading uses
"LLM-as-a-judge and other NLP models"<Cite n={7}/>.

**Ragas.** Describes itself as "Objective metrics, intelligent test generation, and data-driven
insights for LLM apps." On where the data goes: installed from PyPI and run locally. Licence: an
Apache-2.0 badge on its README. Grading is metrics "both LLM-based and traditional," and the
quickstart ships one template today, `rag_eval`, "Evaluate RAG systems," with agent, benchmark,
prompt and workflow templates listed under "Coming Soon"<Cite n={8}/>.

**OpenAI Evals** is the sixth, described apart because it is being withdrawn — and it is the hosted
platform being withdrawn, not the separate open-source repository of that name. OpenAI's
deprecations page gives the dates: announced June 3, 2026, "Existing evals become read-only" on Oct
31, 2026, and "The Evals dashboard and API are scheduled to shut down" on Nov 30, 2026, with a
linked migration path to promptfoo<Cite n={9}/>. Two further eval tools sit in this site's registry
without a description here, Inspect and lm-evaluation-harness. Five is what fits on a page, not a
shortlist.

<Link href="/techniques/evals/">the evals page</Link>, is not a general framework and is not one of

<WhenNot>

Before adopting any of these, try the version that takes an afternoon: twenty questions in a
spreadsheet, the answers pasted in beside them, read by a person. Most teams asking which framework
to pick have not yet written down what a good answer looks like, and a framework will not do that
for them — it will run whatever they have, faster. A tool is worth installing once the same
comparison has to be made repeatedly, or more than one person has to trust the number, which is the
threshold <Link href="/techniques/evals/">evals</Link> sets for building a golden set at all,
applied now to buying instead of writing.

A rubric model is not a shortcut past reading a sample by hand either. Every one of the five above
still needs someone reading a slice of the verdicts, which is what this site's own runner does by
default rather than on request.

</WhenNot>

## How to eval it

<HowToEval>

There is no example on this page, because adopting a framework is a decision rather than a
technique the 60-question set can run. What can be checked is the framework itself, and the check
is the same whichever one is installed: a claim that a system improved needs the same dataset and
the same grading configuration run before and after, a hand-checked sample of any rubric grader's
verdicts, and an honest count of what went ungraded instead of being scored as a failure. If a
tool cannot tell you which of those three it did, that is the finding.

For this site's own runner, `python scripts/eval_run.py --example rag --model stub --dry` projects
what a real run would cost before anything is spent; it is described in full on
<Link href="/techniques/evals/">the evals page</Link>. Whether each tool above offers the same
projection is a question for its own documentation.

</HowToEval>
