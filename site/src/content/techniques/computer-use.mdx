Computer use lets the model operate a real screen: it looks at a screenshot, picks one action —
a click, a keystroke, a scroll — your code carries it out, and a new screenshot goes back.
Anthropic names the mechanism precisely: "the repetition of steps 3 and 4 without user input is
referred to as the 'agent loop'"<Cite n={1}/>, and says in the same sentence what those two steps
are — Claude responding with a tool use request, and your application responding with the results
of evaluating it. OpenAI's own tool repeats the same exchange "until the model stops returning
computer_call items"<Cite n={2}/>, and Google documents your application capturing a new
screenshot and sending it back "to request the next step"<Cite n={3}/>.

One action, requested from one screenshot, is level 4: the model picks it, your code runs it. But
that is not how any maker ships computer use — every real use is the loop itself, exited by the
model, not by your code, which is <Link href="/techniques/single-agent/">single agent</Link>
behaviour, level 5. This page shows one action, on purpose, because that is as far as level 4
goes; treat every screenshot after the first as already the next level up.

This page is marked draft, not published: computer use has no recorded trace and no scored
result file yet, so nothing below is measured. It is illustrated.

<Lane name="use" title="Use it">

If an agent has ever taken over a mouse and keyboard to click through a real application on your
behalf, you have seen computer use. Anthropic, OpenAI and Google each document a tool for it, all
three cited below; the block at the foot of this page names the products and tools registered
against the technique.

All three makers describe the same shape of risk. Screen content is not trustworthy just because
it is on screen: OpenAI is direct about it — "treat screen content as untrusted. Text in a page,
document, or tool result cannot grant permission or override the user's instructions"<Cite n={2}/>.
Anthropic writes that "in some circumstances, Claude will follow commands found in content even
when they conflict with your instructions," and that classifiers scan what the tools return, such
as screenshots, to flag potential prompt injections — which it describes as "an extra layer of
defense" alongside a list of precautions it still asks you to take<Cite n={1}/>. Google offers
"opt-in screenshot scanning to detect hidden adversarial instructions" for the same
reason<Cite n={3}/>.

The three also converge on what to do about actions that cannot be undone. Anthropic lists, among
those precautions, asking "a human to confirm decisions that might result in meaningful
real-world consequences... such as accepting cookies, completing financial transactions, or
agreeing to terms of service"<Cite n={1}/>. OpenAI: "confirm consequential actions. Keep users in
control of purchases, data transmission, destructive changes..."<Cite n={2}/>. Google recommends
avoiding the technique for "tasks involving critical decisions, sensitive data, or actions where
serious errors cannot be corrected"<Cite n={3}/>.

All three also say the environment itself has to be contained, not just the model's judgment: a
"dedicated virtual machine or container"<Cite n={1}/>, an "isolated browser or VM"<Cite n={2}/>, a
"sandboxed VM or container"<Cite n={3}/>. A product that lets an agent click through your own
logged-in browser, rather than a separate one, is not following that guidance.

</Lane>

The example never takes a second screenshot, which is what keeps it at level 4 instead of the
loop every maker's own tool actually runs. The "screen" is text, not pixels — the shape of the
decision is the same either way — and two of its four elements are off limits no matter what the
model asks for:

The model is offered exactly two actions, `click(id)` and `type(id, text)`, and is free to name
any element on the screen, including the two that are not allowed. Nothing in the tool
definitions stops it — `cookie-accept` and `delete-account` are real, well-formed targets. What
stops the click is the allowlist check that runs after the model has already chosen:

The choice itself — the `decided_by: "model"` step — is recorded whether the model names an
allowed element, a forbidden one, or no element at all; refusing it afterward is `decided_by:
"code"`, the same split function calling draws between choosing a tool and running it. If the id
is allowed, the run ends by clicking or typing and reporting what happened; it never asks the

<WhenNot>

Try <Link href="/techniques/function-calling/">function calling</Link> first if the actions
available are a short, named list your code can call directly — a screen only earns its keep when
the interface itself has no API, so operating it like a person is the only way in.

Move up to <Link href="/techniques/single-agent/">single agent</Link> once one action is not
enough — almost immediately, in practice, since a real task on a real screen is a sequence of
clicks and reads, not one. This page's level-4 framing is the building block, not the way
computer use actually ships.

</WhenNot>

## How to eval it

<HowToEval questionCount={0} kinds={[]}>

This example does not answer a question about the document corpus, so the site's 60-question set
has nothing to grade it against. It is registered with the runner as not scored, with that reason
(see `docs/EVALS.md`): asking `scripts/eval_run.py` for it by name prints the reason and stops.
What a real computer-use run is measured on instead: task success (did the sequence of actions
reach the stated goal), the refusal rate on actions outside a stated allowlist, and how often a
run stops at a confirmation point rather than completing an irreversible action on its own. None
of those are one-shot numbers this level-4 slice can produce; they only mean something over the
level-5 loop a real run actually is.

</HowToEval>
