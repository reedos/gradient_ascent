Structured output means the reply comes back in a fixed shape — a JSON object with named fields —
instead of a paragraph your code has to parse by guessing. Makers reach it two ways. A
JSON-Schema response format constrains which tokens the model may produce next, so
the output matches the schema: OpenAI says a model given one "will always generate responses that
adhere to" it, and that there is then "no need to validate or retry incorrectly formatted
responses"<Cite n={1}/>; Gemini takes the same approach through a schema in
`response_format`<Cite n={2}/>. Anthropic gets there differently: define a tool with an input
schema and have the model call it, adding `strict: true` to make the call match
exactly<Cite n={3}/>.

Read the rest of that page, though: OpenAI lists cases where a reply still may not match — a
refusal, or a response cut short by the token limit<Cite n={1}/>. And no schema check speaks to
whether the values are right; a validly typed number can still be the wrong one. Validating your
own side and retrying once, the way Pydantic raises "an error with a breakdown of what was
wrong"<Cite n={4}/>, is still worth doing.

A model released in September 2026 takes the idea to its end. Jev, from TypeSafe AI, generates no
text at all. TypeSafe calls it a System One model, after psychology's fast, automatic System 1:
"a new class of frontier models built to make fast, structured decisions that software can use
directly", or "unstructured state in, typed probabilistic decisions out"<Cite n={5}/>. The
possible outputs are defined in advance, every answer carries a probability, and the result comes
back in one parallel pass instead of word by word; TypeSafe quotes "70ms-500ms" a call<Cite n={5}/>.
The uses it lists are the fixed steps of a level 3 workflow: "classify, route, score, extract, or
branch where hand-written logic is too brittle"<Cite n={5}/>. TypeSafe names three more. Checking
other models: "Score, judge, verify, guardrail, and detect jailbreaks of LLM prompts, reasoning
traces, and/or outputs"<Cite n={5}/>. Reading large piles of data: "Map-reducing over big data"
<Cite n={5}/>. And anything a person is waiting on, where "100ms speeds means you can use AI in
your applications where UX is critical"<Cite n={5}/>; its demo is a bot playing Doom from a text
description of the game at "10 queries a second"<Cite n={5}/>. What it cannot do is write a
sentence, so it replaces the deciding steps in a system and none of the writing ones. It is in early access behind a
waitlist, and the speed, price and accuracy figures are TypeSafe's own. This site has measured
none of them. See <Link href="/timeline/#system-one-models">the timeline</Link> for how it sits
against reasoning models, which went the other way.

This page is marked draft, not published: structured output has no recorded trace and no scored
result file yet, so nothing below is measured. It is illustrated.

<Lane name="use" title="Use it">

You have used structured output any time a product turned something you typed or said into a
form, a calendar event, or a spreadsheet row, rather than just a reply in a chat window. "Add
lunch with Sam Thursday at noon" becoming an actual calendar entry with a title, a date and a
time is a model extracting three fields into a schema, not free text. These features feel
different from chat for exactly this reason: the product asked for a fixed shape, not a sentence.

What separates a good version of this from a bad one is what happens when the extraction is
wrong, not whether it usually works. A well-built feature validates the result before doing
anything with it — a date has to actually be a valid date, a required field has to actually be
present — and either retries automatically or hands the draft back for you to confirm, the way a
calendar app shows a proposed event before saving it. A poorly built one accepts whatever
JSON-shaped thing came back and acts on it immediately, which is how a voice assistant ends up
creating an event on the wrong date with no chance to catch it.

The distinction between "the API guarantees this is valid JSON" and "the values are actually
correct" matters here. A schema-constrained reply is guaranteed to be well-formed: every required
field present, every type right. Nothing about that guarantee checks that the date it extracted is
the date you meant, or that a warranty length pulled from a document matches what the document
actually says. Those checks are still yours, or a person's, to make; the schema guarantee is about
shape, not truth.

When a product fills a form or a record for you, look for a review step before it commits to
anything, especially anything costly to get wrong — a payment amount, a shipping address, a date
on a legal document. Its absence is invisible in a demo; it only shows up the first time the
extraction is wrong.

</Lane>
<Lane name="build" title="Build it">

The example extracts a warranty record for one appliance from
`evals/corpus/warranty-policy.md`: years of full coverage, the years and scope of the limited
warranty that follows it, and how many days of coverage apply to commercial or rental use. The
schema is five fields, all required.

<CodeFile file="examples/structured_output/run.py" func="run" />

The retry is deliberately capped at one. `_validate` checks the reply for every required field,
checks that the appliance named in the reply matches the one that was actually asked about (a
model can return well-typed JSON about the wrong appliance), and checks that the numeric fields
are really integers rather than, say, the string `"90 days"` — a mistake a schema does not always
catch, depending on how strictly the backend enforces it. If the first reply fails validation, the
code appends the specific problem to the conversation and asks once more; a schema-constrained
backend makes the second reply far more likely to be correctly typed, but this example's own
check does not assume that and validates the second reply again regardless. If it is still
invalid, the run reports that plainly instead of returning something that never actually passed.

Every step is `decided_by: "code"`: the schema is fixed, the retry count is fixed, and the model
only ever chooses the field values inside whatever shape it was given. Compare this with
<Link href="/techniques/function-calling/">function calling</Link> at level 4, where the model
additionally decides whether to use a schema-shaped tool at all — the schema there is the same
idea, but the decision of when to reach for it moves from your code to the model.

<WhenNot>

Skip the schema, and just read the reply as text, if nothing downstream actually parses it — a
chat app showing an answer to a person does not need JSON. And if the field you need is already
typed in a fixed, unambiguous format (a form field a person filled in directly, a part number a
barcode scanner read), <Link href="/techniques/order-zero/">level 0, no model at all</Link> reads it directly,
with no model and nothing to validate.

</WhenNot>

## How to eval it

<HowToEval questionCount={60} kinds={['lookup', 'multi-hop', 'numeric', 'unanswerable', 'conflicting sources']}>

Structured output adds a check no plain-text reply can be given: whether the reply is valid
against its schema at all, tracked separately from whether the values in it are right. A run can
score well on validity and badly on the values, or the reverse, and the two numbers together say
more than either alone. Count the retries as a third number. A schema that needs a second
attempt on a third of its inputs is a schema to rewrite, not a model to replace.

This example extracts a fixed warranty record rather than answering the question it is handed,
so `scripts/eval_run.py` will not score it against the site's 60-question set; asking prints
that reason and stops (`docs/EVALS.md`). The set that would measure it is a different one: a
list of passages, each with the record it should produce. Score valid-JSON rate, accuracy field
by field against those records, and how often the retry was needed.

</HowToEval>
