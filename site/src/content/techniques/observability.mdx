Observability is recording what each run did, in enough detail that a bad result can be traced
back to the step that caused it: which passages a retrieval step picked, which tool a model
called and with what arguments, which branch a workflow took, and how many tokens and how much
time each step spent. OpenTelemetry, an open standard for this, defines a trace as "the path of
a request through your application" and a span as a unit of work that is one of "the building
blocks" of a trace, carrying attributes, its own "key-value pairs" of metadata about the
operation it tracked<Cite n={1}/>.

This topic is not a level on the ladder; it applies at every level, the way
<Link href="/techniques/safety/">safety</Link> and <Link href="/techniques/ops/">ops</Link> do.
What is worth recording changes by level, which is why this page has its own "At each level"
section rather than pointing only at ops's.

This page is marked draft, not published: no result file or production trace exists for this
site, so nothing below reports a measured number. What it can show is the mechanism, and the
site's own small version of it.

<Lanes>
<Lane name="use" title="Use it">

If a product you use shows "thinking" steps, tool calls, or a "sources" panel while it works,
that is observability surfaced to you directly: a trace the product recorded for its own
debugging, with a reader-facing view built on top. When an answer looks wrong, that panel is
where to look first — which step, if any, went off track — rather than only rereading the final
text.

The same question a builder asks of a system applies to a product you did not build: can you
tell, after the fact, which step produced a wrong answer? A chat app that shows only a final
message gives you nothing to check but plausibility. One that shows retrieved sources, the tool
calls it made, or a citation trail gives you something to check against, the same distinction
<Link href="/techniques/reviewing/">reviewing</Link> makes about a result in general.

Cost and time are also worth watching, not just correctness. If a product's answers are slow or
it hits a usage limit, that is very often one expensive or malfunctioning step, not the whole
system being slow. Without a per-step view there is no way to tell "one bad step" apart from
"everything is slow" from the outside — and per-step numbers are also what
<Link href="/techniques/cost-optimization/">cost optimization</Link> needs before it can say
which lever would help.

Sampling is what makes this affordable at any real volume: OpenTelemetry describes sampling as
"one of the most effective ways to reduce the costs of observability without losing visibility,"
and distinguishes a decision made "as early as possible" (head sampling) from one made only
after "considering all or most of the spans within the trace" (tail sampling)<Cite n={2}/>. A
product that traces everything, forever, at full detail either has very little traffic or is
about to have a very large bill.

</Lane>
<Lane name="build" title="Build it">

This site's own `trace.json`, written by `examples/common/trace.py`, is a small version of the
same idea: an ordered list of steps, each with a `kind`, a `decided_by`, a title, a detail
string, token counts, a duration in milliseconds, and which edge style it draws — solid for
code, dashed for model:

What a step's `detail` holds is exactly the "what NOT to log" question. Four things do not belong
in a trace by default: personal data about a customer, any secret pasted into a message, whole
documents or retrieved passages, and prompt and answer text itself. The first three are usually
obvious once someone asks; the fourth is the one that gets left on, because it is the most useful
field to have when debugging.

OpenTelemetry's own conventions treat it as the separate, riskier case it is. The attribute that
carries the chat history, `gen_ai.input.messages`, is marked with the requirement level `Opt-In`
and noted as "likely to contain sensitive information including user/PII data"<Cite n={3}/>.
`Opt-In` is defined elsewhere in the same specification, and it is a strong default:
"Instrumentations SHOULD populate the attribute if and only if the user configures the
instrumentation to do so. Instrumentation that doesn't support configuration MUST NOT populate
`Opt-In` attributes."<Cite n={4}/>

`examples/observability/run.py` shows the same shape working on a real trace: `to_otel_spans`
turns this site's own step list into span-shaped dictionaries named the way OpenTelemetry's own
generative AI conventions name them — `gen_ai.operation.name`, `gen_ai.usage.input_tokens`,
`gen_ai.usage.output_tokens` — so a trace this site already records could be handed to any
OpenTelemetry-reading backend instead of only this site's own player. Those three names are
copied from a specification whose own status line reads Development as of the date above; nothing
here claims to implement a finished standard, only to borrow its attribute names<Cite n={3}/>.

The content question is a parameter, not an afterthought: `capture_content` defaults to `False`,
so a step's `detail` never reaches the returned spans unless a caller turns it on deliberately.
`tests/test_example_observability.py` pins that a secret planted in a `detail` is absent from the
default output and present only when `capture_content=True`. Three attacks on that redaction are
worth knowing about, and the same test file pins all three. A `detail` is free text — it can hold
a retrieved passage, a tool call's arguments, or an error message that quotes the prompt back —
so redaction has to cover the field, not a list of the things people expect to find in it. A
captured `detail` goes to this site's own `gradient_ascent.detail`, never to
`gen_ai.input.messages`, which the specification defines as a structured list of messages: the
right attribute name for the wrong shape of value misleads a backend rather than informing it.
And a step's `title` becomes the span name with no redaction at all, which is why a title on this
site names a tool or a section and is never built out of content.

Redaction at export is also the last place it can happen, not the first. Turning it on today does
nothing about a `trace.json` written yesterday with content already in it, and a trace store is
much easier to fill than to clean.

Linking a trace to a scored result is a join on fields both already carry: this site's
`trace.json` records a `commit`, and a result file under `evals/results/` (see
`docs/EVALS.md`) records its own `commit` and `run_date` alongside `citation_hit_rate` and
`tokens_in`/`tokens_out`. No such pair exists yet — no example has a recorded trace or a
non-stub result file — but the fields to join them on are already there on both sides. Run it
yourself:

<WhenNot>

Skip a tracing format, sampling policy and content-redaction rule for a single script you run
yourself and read the output of directly — the terminal you are looking at already is the trace.
Add structured tracing once a system runs unattended, has more than one or two steps that could
each go wrong differently, or is used by someone other than the person who can read its logs.

Skip building a tracing format of your own at that point, too. This site's own `trace.json`
exists to step through one recorded run on a page; a real deployment should reach for a standard
such as OpenTelemetry, which many backends can already read, rather than growing a bespoke shape
and migrating off it later.

If every call already goes through <Link href="/techniques/ai-gateways/">an AI gateway</Link>,
some of this is being recorded for you at that hop: one log line per call, with the token counts
and which provider answered. What a gateway cannot see is what happened between calls — the
retrieval, the tool result, the branch your own code took — which is the part a trace is for.

</WhenNot>

## At each level

- <Link href="/levels/0/">No model</Link>: there is nothing to trace that a normal application
  log does not already cover — this topic's own concerns start at level 1.
- <Link href="/levels/1/">One call</Link>: one span, the way
  <Link href="/techniques/chat/">chat</Link>'s own trace is a single model step; the whole
  question is whether that one call's tokens, time and outcome are recorded at all.
- <Link href="/levels/2/">Context</Link>: what got retrieved is now part of the trace, not just
  the model call — <Link href="/techniques/rag/">RAG</Link>'s own citations are exactly the
  record a reviewer needs to check an answer against its sources.
- <Link href="/levels/3/">Workflows</Link>: a fixed number of steps means a trace can be
  compared against the pipeline's own diagram directly — a step that is missing or repeated is
  visible without reading a single token of content.
- <Link href="/levels/4/">Tools</Link>: a tool call's arguments and result belong in the trace
  as their own step, not folded into the model step around them, since a wrong argument and a
  wrong model answer are different failures that need different fixes.
- <Link href="/levels/5/">Agents</Link>: the number of steps is no longer fixed, so a trace is
  the only way to know how many turns a run actually took and where it stopped, the same
  uncertainty <Link href="/techniques/single-agent/">a single agent</Link>'s own `max_steps` is
  built to cap.
- <Link href="/levels/6/">Teams of agents</Link>: several agents produce interleaved traces, so
  which agent decided what has to survive being merged into one timeline, the way
  <Link href="/techniques/agent-graphs/">agent graphs</Link>' own handoffs need to be
  attributable to a specific agent after the fact.
- <Link href="/levels/7/">Always-on agents</Link>: nobody is watching a run as it happens, so
  the trace is the entire record a person has after the fact — sampling policy matters most
  here, since a dropped trace from a system like
  <Link href="/techniques/agent-teammates/">an always-on assistant</Link> cannot be reconstructed
  by asking the model again.

## Practices

- Record tokens in, tokens out and wall time per step, not only per request, so an average
  latency number cannot hide one consistently slow step.
- Default to not capturing prompt or answer content, and make capturing it an explicit, separate
  choice — the requirement level OpenTelemetry marks its own message-content attributes with.
- Keep content out of the fields nobody thinks of as content: a span's name, a step's title, an
  error string that echoes what was sent. Redaction that covers one field and not those is a
  policy with a hole in it.
- Give every trace and every scored result a shared id to join on (this site uses the commit
  the code was at), so a bad result can be traced back to a run without guessing which one it was.
- Bias sampling toward keeping the traces most worth reading — slow, expensive or failed runs —
  rather than a uniform random sample that treats an incident the same as an ordinary request.
- Read the built trace against the pipeline's own diagram after any change to the code that
  produces it, the way this site's own tests check a trace's `decided_by` pattern against the
  level it claims to be.
